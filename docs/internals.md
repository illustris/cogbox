# Internals

How cogbox wires a per-user, per-instance sandbox out of a single prebuilt VM image. Useful when debugging, or when extending cogbox itself.

## Directory layout

Each instance has its own config dir under `~/.config/cogbox/instances/<name>/`. The default instance uses the reserved name `default`, so the config layout mirrors the data layout:

```
~/.config/cogbox/
  authorized_keys              # shared SSH keys (fallback for all instances)
  instances/
    default/
      config.json              # default instance settings (sshPort 2222)
      flake/
        flake.nix              # per-instance NixOS extensions (no-op default)
      plugins-flake/
        flake.nix              # GENERATED plugin composition (only with plugins)
      runner.path              # fast-path record: key, composed runner, comp
      apply/                   # live-apply boot state (see "Boot snapshot" below)
        snap/<id>/             #   snapshots; base -> the one the running guest booted
        pin/<id>/              #   composition copies a re-exec evaluates
        trash/                 #   retired snapshots, emptied by init passes
      gcroots/
        booted                 # GC root of the runner the last boot ran
        applied/               # runners built during that boot (released at the next)
      l7-ca/                   # per-instance L7 terminate CA (key never leaves host)
    work/
      config.json              # auto-generated with unique ports
      flake/
        flake.nix
      authorized_keys          # optional per-instance SSH keys
```

SSH keys fall back to the shared top-level `authorized_keys` unless a per-instance file exists. At launch, cogbox's own public key (`~/.local/share/cogbox/cogbox_ed25519.pub`, see below) is unioned into whichever file is used, so `cogbox ssh` always has an authorized identity.

Data (VM state, overlays) is stored per-instance under `~/.local/share/cogbox/instances/<name>/`. All instances are siblings, so a default-instance boot does not 9p-share named-instance state into the default guest:

```
~/.local/share/cogbox/
  cogbox_ed25519             # cogbox's own SSH key; default identity for `cogbox ssh`
  cogbox_ed25519.pub         # its pubkey, unioned into each guest's authorized_keys
  instances/
    default/
      harness-overlay.img      # shared ext4 overlay for all harnesses
      .config/active-harnesses # newline-separated list of active harnesses
    work/
      harness-overlay.img
```

The keypair sits in the data-dir root, a sibling of `instances/`. Only `instances/<name>/` is 9p-mounted into a guest, so the private key never enters the sandbox. It is generated automatically and reused across all instances; generation is idempotent and re-runs on every launch, so an existing setup gains the key on upgrade and a deleted key is regenerated. `--no-auto-keys` at first init skips generation and writes a durable opt-out marker (`~/.config/cogbox/no-cogbox-key`) so a later plain launch does not re-create the key. The Zig `ssh` and `start` verbs pin ssh to it -- `ssh -i <data>/cogbox_ed25519 -o IdentitiesOnly=yes -o IdentityAgent=none` -- so the user's agent and `~/.ssh` keys are not offered and no agent is contacted (a gpg-agent can't stall or prompt on connect). Under `--no-auto-keys`, where the key is absent, ssh falls back to the user's agent and `~/.ssh` keys.

## Runtime directory and 9p shares

Static QEMU 9p share sources use build-time sentinel paths that the wrapper rewrites into a per-instance symlink directory, so the built VM image works for any user. Launch-only `--add-dir` and `--add-dir-ro` grants use the MicroVM runner's runtime argument hook instead: the wrapper canonicalizes each selected source, stages it behind a numeric alias, and passes only fixed alias-based QEMU tokens. Runtime state lives under `$XDG_RUNTIME_DIR/cogbox` (typically `/run/user/$UID/cogbox`); named instances append a `-<name>` suffix. Each has its own symlinks and PID lock:

```
$XDG_RUNTIME_DIR/cogbox[-<name>]/
  data/                  -> $COGBOX_DATA/instances/<name>
  claude-code-config     -> $COGBOX_CLAUDE_CONFIG
  claude-code-auth       -> $COGBOX_CLAUDE_AUTH
  opencode-config        -> $COGBOX_OPENCODE_CONFIG
  opencode-data          -> $COGBOX_OPENCODE_DATA
  codex-home             -> $COGBOX_CODEX_HOME
  hermes-agent-home      -> $COGBOX_HERMES_HOME
  omp-home               -> $COGBOX_OMP_HOME
  pi-home                -> $COGBOX_PI_HOME
  additional-dirs/
    0                   -> first canonical --add-dir/--add-dir-ro source
    1                   -> second canonical source
  additional-dir-args   # executable producing fixed alias-based -fsdev/-device tokens
  system-additional-dirs # fw_cfg JSON: tag, same-path guest target, read-only mode
  .harness-stubs/        # empty stubs for inactive harnesses (so QEMU
                         # 9p sources resolve even when the host has no
                         # state for a given harness)
  console.sock           # guest serial console (Unix socket)
  monitor.sock           # QEMU HMP monitor (Unix socket)
  netfilter-rules        # rendered L4 + remap runtime rules
  l7-rules               # rendered L7 runtime rules
  console.log            # captured guest serial output
  cogbox.log             # daemon stdout/stderr (passt, QEMU warnings); kept on a failed start for post-mortem
```

If `$XDG_RUNTIME_DIR` is unset and `/run/user/$UID` doesn't exist (no active logind session), the wrapper falls back to `/tmp/cogbox-runtime-$UID/` per the XDG spec.

The numeric aliases and their manifest exist for one VM lifetime. Cleanup waits for QEMU to exit before deleting `additional-dirs/`, `additional-dir-args`, and `system-additional-dirs`, even when a crashed launch retains the rest of the runtime directory for logs. A later flagless launch stages an empty manifest and exposes none of the prior paths.

`cogbox delete [-n <name>]` removes all three of these per-instance trees -- the config dir, the data dir, and the runtime dir -- for one instance. It refuses while the instance is running (stop it first) and prompts before removing anything unless `-y` is given.

## Guest Nix store

On a VM guest (local and hosted) `/nix/store` is an overlay: the lower is the host's whole `/nix/store`, read-only over 9p at `/nix/.ro-store`, and the upper is `/nix/.rw-store/store`. The guest DB registers only the guest closure, so under a plain local store every other host path looked like an invalid path to `nix store gc` (and `nix-collect-garbage`, `nix-store --gc`), which walked it over 9p and left a whiteout for it in the upper, freeing nothing. The guest therefore runs Nix's experimental `local-overlay://` store, which deletes only what is in the upper layer: GC reclaims guest-built and guest-fetched paths, and host paths outside the guest closure stay visible but unregistered.

The lower store's metadata DB is built at boot by the `cogbox-overlay-store` script, which a `boot.postBootCommands` fragment runs (ordered before microvm.nix's own `--load-db`), from the same `regInfo` closure registration, into `/nix/.rw-store/lower-state`, so it is exactly as ephemeral as the upper. It cannot be a build-time derivation: it would close over the toplevel that carries `nix.conf`. The `store =` line reaches `nix.conf` through `!include /run/cogbox/nix-store.conf`, which the script writes only after it has checked that the `/nix/store` mount's lowerdir and upperdir are `/nix/.ro-store` and `/nix/.rw-store/store` (allowing the `/sysroot` or `/mnt-root` prefix stage 1 leaves in `/proc/mounts`, which is why Nix's own verbatim `check-mount` is off) and `nix store info` has opened the overlay store. Any failure leaves the guest on the plain local store with a boot-log warning, and the failing step's stderr in `/run/cogbox/nix-store.err` (absent on success). The container target does not use this (its `/nix` is cogworx's CoW overlay). `checks.cogbox-vm` Phase B covers it.

The same script has a live mode for the [live switch helper](#guest-helper-cogbox-live-switch): `cogbox-overlay-store --live /nix/.rw-store/lower-state.<n> REGINFO...` builds a fresh lower DB generation from the given registrations and repoints `nix-store.conf` at it only once the store opens over it, so a failure leaves the store on the generation nix-daemon already uses. The boot run removes the `lower-state.<n>` generations an earlier boot left on a persistent upper.

## Boot-only units (once-markers)

A NixOS configuration switch starts every active target again, and starting a target also starts every unit it wants that is not active: a oneshot without `RemainAfterExit`, a unit its condition skipped, a unit that failed. Some VM guest units do work that belongs to the boot alone and must not run again on a guest in use: the mount and directory preparation (`cogbox-additional-dirs`, `cogbox-vm-sshd-prep`, `harness-setup-dirs`, `harness-overlay-img`, `resize-store-overlay`, `cogbox-guest-dirs` and nixpkgs' `rw-<mount>` overlay pre-mount units), the pool migrations (`cogbox-guest-work-migrate`, `cogbox-guest-harness-migrate`) and the runtime tool restore (`cogbox-runtime-restore`). Each one the guest declares carries `ConditionPathExists=!/run/cogbox/once/%N`.

`cogbox-boot-settled.service` writes those markers. It is `Type=exec`, wanted by and ordered after `multi-user.target`, and runs `systemctl is-system-running --wait`, which returns once the boot's job queue has drained. If the state is then `running` or `degraded`, it writes `/run/cogbox/once/<unit>` for each listed unit whose start this boot attempted (its `ConditionTimestampMonotonic` is set) and that did not fail (`Result=success`; a unit its own condition skipped counts as started). Until then the condition holds, so the boot runs these units exactly as before; afterwards a later start of a marked unit in the same boot is skipped (inactive, condition failed). A unit the boot never started (a dependency failed, or nothing wanted it) or one that failed gets no marker and keeps today's behaviour. A [live apply](#live-plugin-apply) reads the markers the guest holds: a start it would propagate to a listed unit without one refuses the apply (`restart_only_units`). A boot that does not settle writes nothing. The script always exits 0 and logs one line naming the units it marked, so it can never degrade the system. The markers live on the `/run` tmpfs, so every boot starts without them. The service requires, precedes and gates nothing.

Units that something restarts on a running guest are deliberately not in the list: `cogbox-claude-stub` (restarted by the control plane after a Claude connect), `cogbox-reply-route`, `cogbox-brain-materialize`, `cogbox-l7-trust` and `sshd`. With a marker, each of those restarts would become a stop. The container target has neither the markers nor the service. `checks.live-apply-prereqs` pins the list against the realized unit files and runs the marker script against a stub `systemctl`.

## Live plugin apply

Applying a plugin change to a running VM sandbox without relaunching QEMU. What ships so far is the [boot snapshot](#boot-snapshot-live-apply-state), the [once-markers](#boot-only-units-once-markers), the guest helper, the host's snapshot and rollback code, and the host verb `cogbox plugin apply` (preflight, build, plan, the guest phase, the records and rollbacks, and the recovery of an interrupted apply). It is wired into the CLI, `cogbox stop`, `cogbox delete`, the launcher and the GCE/PVE wrapper and supervisor ([below](#plugin-changes-stop-delete-and-the-launcher)). [Apply anyway](#apply-anyway-host) (`--force`, `--force-plan`) forces a plan the owner has seen.

### Guest helper (cogbox-live-switch)

Every VM toplevel links `cogbox-live-switch` at its root, and the host always runs the booted system's copy, `/run/booted-system/cogbox-live-switch`, over ssh as root, so every hop of one boot runs the same helper whatever system is current. The container target has none. The helper switches the guest from its current system P to a new toplevel T that the host built (the toplevel of the runner the next boot would boot), one generation G at a time, and reverts on its own unless the host confirms.

Host-facing verbs:

- `settled --wait N`: long-polls (at most 30 s) until `systemctl is-system-running` is `running` or `degraded` and the job list is empty.
- `plan T`: `busy` (with the active generation) or `guest_tainted`, or the guest data the host's unit plan uses only to refuse: the boot id, the booted and current systems, the store mode (`overlay`, or `fallback` when `nix-store.conf` is missing or `nix-store.err` exists), `T/bin/switch-to-configuration dry-activate` run in a transient unit bounded at 60 s (its refusals, the units it would stop, skip, reload, restart and start, and whether it would restart systemd), the state of every loaded unit (`inactive` for exactly `inactive`, `active` for one that runs: `active`, `reloading` or `refreshing`; `notfound` for one systemd cannot load), every once-marker present in `/run/cogbox/once`, the induced starts (inactive or failed units an active target wants at runtime, once-marked ones included: the host decides what a marker skips), and the runtime reverse edges of every loaded unit (`RequiredBy`, `BoundBy`, `ConsistsOf`, `PropagatesStopTo`, `PropagatesReloadTo`, `ConflictedBy`). The reply is not capped in the guest; the host caps it at 8 MiB.
- `start G T REGINFO --prev P --boot-id ID --bound S --window W [--force-units FILE|-] [--repair cogbox-reply-route.service]`: under `/run/cogbox/live-apply/lock`. A G already recorded this boot (an abort's tombstone included) answers its recorded state and arms nothing; otherwise it refuses `stale_boot`, `guest_tainted`, `busy` (another generation is active) or `superseded` (the current system is not P). It then arms the dead-man before any mutation, `systemd-run --unit=cogbox-live-revert-G --on-active=Ws`, and starts the apply unit detached, `systemd-run --no-block --collect --unit=cogbox-live-apply-G -p RuntimeMaxSec=S -p ExecStopPost='... settle G' ... run G T REGINFO`, and returns in about a second. Nothing depends on the ssh session. The forced units (one per line, from a guest file or stdin) are charset-checked again and journaled; `--repair` accepts only `cogbox-reply-route.service`.
- `status G --boot-id ID [--wait N]`: the state, and in every state the recorded refusal, verdict or revert cause; `--wait` (at most 30 s) returns at once on `switched` or a terminal state and otherwise as soon as the state, verdict or cause changes. A different boot id answers `stale_boot`.
- `abort G --boot-id ID`: reverts a generation that has no verdict or cause yet (cause `aborted`, with `during_activation=yes` when the switch was running); a no-op once one is recorded. For a G this boot never saw it writes a `stale` tombstone under the lock `start` takes, so a `start` of G still in flight from a dead host verb answers `stale` and arms nothing.
- `confirm G --boot-id ID`: `switched` becomes `confirmed`, under the generation's lock that the revert also takes, and the dead-man is disarmed.
- `log G`: the guest log of G (its units' output and both switches'), control characters removed, at most 64 KiB. The host keeps it in `<G>.guest.log` and never exports it.

Every other reply is `key=value` lines between `proto=2` and `end=1` (a reply without `end=1` was cut off), and every value is an enumerated token, an integer, the generation, the boot id, a store path of the booted or current system, or a unit name that passed a charset check (the host intersects unit names with T's and P's unit files, and reports a template instance only by a name T or P gives it, else as its template). No guest free text crosses: the helper's diagnostics stay in the guest. Exit 0 for every answered request, 64 for a usage error.

The apply unit runs `run G T REGINFO`:

1. **Register**, under `flock -x -w 30 /nix/var/nix/gc.lock` (busy: refused `busy_gc`) and bounded at 150 s: the guest GC root `/nix/var/nix/gcroots/cogbox-live/G` to T, then a fresh lower DB generation `/nix/.rw-store/lower-state.<n>` from the boot regInfo, every regInfo applied this boot and T's (`cogbox-overlay-store --live`), `nix-store.conf` repointed at it, `systemctl restart nix-daemon` (60 s), and every generation removed but the new one and the one the conf named before (a daemon worker forked before the restart still reads that one). Generation numbers are never reused and the current one is read from the conf, so a registration that failed partway never makes a later one prune the generation in use. A plain `--load-db` into the running overlay store is not an option: it would register T's paths in the upper DB while their files are in the lower, and once such a path is garbage the local-overlay GC, finding it invalid in the lower DB, deletes it through the overlay mount, which leaves a whiteout that hides the host path from the guest.
2. **Visibility**: every path in T's closure (`store-paths` beside REGINFO) must be visible through the overlay, after one `drop_caches` retry for 9p lookups cached before the host built them; checked before registering too, so a hidden closure is never registered. Otherwise refused `store_path_hidden`, or `store_whiteout` when a whiteout in the upper hides it. The fallback store refuses `store_fallback`.
3. **Snapshot** the units of the unit plan's classes A-C that systemd lists, matched by stem as the plan matches them (`docker.socket` with `docker.service`), minus the forced and repair units, `sshd@` and the login-session units (every login starts one, the login probe's included): each one's state, InvocationID and whether a unit file or generator source backs it (mounts that only mirror the kernel's mount table come and go on their own, and are compared by nothing below), and the network health: the uplink's IPv4 address, the reply rule (`ip -4 rule` priority 50) and the `cogbox_reply` table ([guest reply routing](#guest-reply-routing)).
4. **Switch**: `T/bin/switch-to-configuration test`. Exit 100, a pre-switch exit 1 and "Could not acquire lock", with no "stopping the following units" or "activating the configuration" line, are the no-op refusals `init_interface`, `pre_switch_check` and `switch_locked`.
5. **Repair** (`--repair`, sent with a forced plan that has a class C unit or `firewall.service`): `systemctl restart cogbox-reply-route.service`, because an nftables start can flush the whole ruleset, the reply table included (`networking.nftables.flushRuleset`, the default once a ruleset is set), and a firewall start rewrites what the boot ordered before the reply route. (Enabling nftables at all is never live: it blacklists `ip_tables`, which changes the initrd, so tier 1 answers `kernel_modules`.)
6. **Post-checks** on exit 0, 2 or 4: sshd and `cogbox-brain-materialize` active, `sshd -t` (run with the running sshd's own binary, `/proc/<MainPID>/exe`, which serves every new login, else the booted system's), a login probe (`runuser -l root -c true`, 20 s), the snapshotted units undisturbed, and network health no worse (sampled again after 5 s). A protected unit is disturbed when a running one has a new InvocationID or none (restarted, or unloaded), or, having none to compare (a mount the initrd made), gets one; when a running one with a source stops running or is gone from the list (systemd keeps the last InvocationID of a stopped unit that stays loaded, so only its state shows the stop: a plugin unit's `ExecStartPre=systemctl stop systemd-resolved.service`, an activation snippet's `systemctl stop docker`), except a mount its running automount unmounted when idle; when one with a source that did not run before (inactive, failed, or not loaded at all, as a unit a new generator writes at the daemon-reload) runs, is starting, stopping or failed, or got a new InvocationID (a oneshot that ran and exited), except a `dbus*` activation, `systemd-logind`, `cogbox-reply-route` and a mount its running automount triggered, whose start the plan allows; and when switch-to-configuration reports it failed, unless it was failed before the switch with the InvocationID it still has (it lists every unit failed at its end, one that failed at boot too). A unit systemd cannot report after the switch counts as disturbed. `podman.service` is left out of the stop, start and InvocationID comparisons while `podman.socket` ran through the whole switch (active after it, with the InvocationID it had before): the API service is socket-activated and `podman system service` exits after 5 s idle, so a docker-API client polling during a switch (`docker compose ps`, testcontainers, an IDE's Docker extension) stops it, starts it or gives it a new InvocationID, none of it the switch's, and its containers run under conmon in their own scopes, not under it. A reported failure of it still counts, and so does any change to it once the socket was restarted or stopped. The plan refuses a switch-driven change to its own unit (class B); the remaining gap is an activation snippet's `systemctl restart podman` while the socket stays up, which the post-check does not catch. This is the backstop for starts the plan cannot see: generator output, activation snippets, generator-only edges. A failed base check is `failed` with verdict `breaks_base` (`activation_failed` on exit 2); otherwise a disturbed protected unit is `unplanned_disruption` and, on exit 4, a failed forced unit is `forced_unit_failed` (both name the units); otherwise `switched`, with the exit code and the failed units reported. Any other exit is `failed` with `exit_<n>`, unless the activation had begun (a "stopping the following units" or "activating the configuration" line) and a base check fails: then `breaks_base`, which the host rolls back, where `exit_<n>` keeps the change for the next boot.

The apply unit's `ExecStopPost`, `settle G`, reads G's state, never the current system: `starting` (the unit ended before the switch) is refused `run_failed`; `failed` reverts; `switching` (the switch was killed by its bound or died) records the phase from switch-to-configuration's progress lines, `stop_hang` while stopping units, `activation_hang` while the activation script ran, then, once activation returned, `unit_hang` when a pending job is on a unit this apply brought (new in T, or its unit files differ from P's; named) and `switch_timeout` otherwise, and reverts. `revert G` (the dead-man unit, which settle and abort start early) takes the generation's lock (three waits of 20 s: the dead-man fires once) and the generation to `reverting`, stops the apply unit, and, when the switch had begun, runs `P/bin/switch-to-configuration test` with retries on a busy switch lock (at most 240 s inside 300 s), repeats the repair in a forced run (at most 60 s), and ends `reverted` when P is current with sshd and the brain active and an exit of 0 or 4, else `revert_failed`. A current system that is neither P nor T was switched by something else: the revert leaves it alone and ends `stale`. Every leg is budgeted to end 30 s before the revert unit's 360 s bound (the switch leaves 10 s for the checks, and 20 s more for a forced run's repair; the repair gets what is left, at most 60 s), so the bound never cuts a leg and the revert records its own end: one out of time ends `revert_failed` with the switch's exit 124. A revert cut short by its bound anyway ends `revert_failed` from its own `ExecStopPost`.

States, per generation under `/run/cogbox/live-apply/gen/G/lock`: `starting` goes to `switching`, `refused` or `reverting`; `switching` to `switched`, `refused`, `failed` or `reverting`; `switched` to `confirmed` or `reverting`; `failed` to `reverting`; `reverting` to `reverted` or `revert_failed`; any of them to `stale` from a revert only. `refused`, `confirmed`, `reverted`, `revert_failed` and `stale` are terminal and sticky; entering one removes the guest root and disarms the dead-man, and `revert_failed` also writes `/run/cogbox/live-apply/tainted`, after which every `plan` and `start` of the boot answers `guest_tainted`. A recorded verdict or cause is never replaced. Everything lives on the `/run` tmpfs, so each boot starts clean.

Bounds: the apply unit `RuntimeMaxSec=S` (840 s by default: gc.lock 30, registration 150, the switch and its checks the rest), the dead-man W after `start` (S + 120 by default), the revert unit 360 s, dry-activate 60 s, the long-polls 30 s. `checks.live-switch-helper` drives every verb against stand-ins for systemd, `ip`, `nft`, sshd and the store setup.

### Snapshots and automatic rollback (host)

A live apply that proves a plugin change broken rolls the host's plugin state back, so the next boot does not include the change. The code is `zig/src/plugin/snapshot.zig` and `zig/src/plugin/rollback.zig`; everything runs under the instance config lock and is file operations only (no nix, no child process).

- **Snapshots** have the shape of the [boot snapshot](#boot-snapshot-live-apply-state), and `snapshot.take` writes one in Zig for the apply's S: byte copies of the composition, `state.json`, `src/` as a hard-link copy of `plugin-sources/` made natively (directories and symlinks recreated, a directory's mode and, as root, its owner kept as `cp -a` keeps them; a device, fifo or socket fails the take), then `meta.json`. A take that fails or outlives its bound leaves no `meta.json`, so the GC collects it. `snapshot.read` refuses an incomplete snapshot and one whose composition bytes no longer hash to its `comp`. Roles flip by an atomic symlink rename and are never pointed at an incomplete snapshot. The Zig GC uses the launcher's keep rules (`base`, `built`, `booting`, the 16-hex strings in `apply/active`, `apply/inflight.json` and the intents; one that does not parse keeps everything), and an intent's tmp name, written by an apply-flock holder that may not hold the config lock, keeps what it names too. Under sudo new names go to the invoking user.
- **Scope.** A plugin's identity is its presence plus `url`, `attr`, `lockedUrl` and `narHash`. Against the target snapshot Z (`base` for a live rejection; `built`, else `base`, for an `eval_error`), every name whose identity differs from S is `removed` (a rolled-back add), `restored` (an update) or `reinserted` (a del). The scope, with the revs and narHashes involved, travels in the intent, so the fail-closed tier and the record need no snapshot.
- **Intent.** `apply/rollback/<G>.intent` = `{G, op, reason, target, target_id, scope}`, written only when G has no record: the content goes to `.<G>.intent.<nonce>.tmp`, is fsynced and `link(2)`ed to the final name, so a crash leaves no intent or a complete one. Only a finish whose caller holds the apply flock removes a leftover tmp name. An intent that does not parse is never discarded; it counts as an unfinished rollback.
- **Finish** (`rollback.finishPending`, bounded at 240 s, never taking the lock itself): `plugin-sources/` := a hard-link copy of Z's `src/` renamed into place (the old tree into the trash); config.json's plugin entries := Z's and the tagged policy narrowed per name (below); `plugins-flake/` := Z's composition bytes, or removed; `runner.path` := Z's runner only when Z recorded one under the current `COGBOX_FLAKE_SOURCE#COGBOX_REEXEC_PACKAGE` and has a composition, else removed; the policy reloaded only in rules mode and best-effort once saved; `apply/built` unlinked for a live rejection (an `eval_error` keeps it); then the record, the intent delete and the snapshot GC. Every step is a target-state assignment, so a crash anywhere is finished by the next call. A failure restoring the sources, config, composition or runner switches, in the same call, to the fail-closed tier: every `removed` and `restored` name loses its entry, its tagged allows and injections (a `removed` name its denies too) and its source, `flake.nix` is regenerated, those names' root inputs are dropped from `flake.lock` (an unparseable lock is unlinked), and `runner.path` and `apply/built` are removed; a `reinserted` name stays deleted (one the normal tier already put back loses its entry, source and root input again, and keeps the policy the normal tier left, which only narrows). If that fails too, the intent stays and the finish reports it pending.
- **Policy.** A rollback never re-grants. A `removed` name loses every tagged entry, denies included, which is policy as it was before the add. For `restored` and `reinserted` names an allow carrying `"approved": true` stays (only `rules add --plugin` and `l7 add --plugin`, the approval path, write it; a plugin's merge strips it), every other allow and every injection := C intersect Z (`mutate.sameRule`, whose inject identity is host, secret, style, cookieName and port; C's element kept), and denies := C union Z (Z's missing denies prepended). `policy_not_restored` counts Z's allows and injections not in C.
- **Records.** `apply/rollbacks.jsonl` keeps the last 64 records `{seq, gen, op, reason, at, target, target_id, status: done|removed, names: [{name, action, from_rev, to_rev, from_nar_hash}], policy_not_restored, repeat}`, one per generation, rewritten as a new file. A new records file first gets a new random `apply/rollbacks.id`, so a reader notices one whose seqs restart. `repeat` counts earlier records that rolled back the same name at the same narHash. `apply/audit.log` (1 MiB, the newest half kept past it) mirrors the records and the abandons.
- **Abandon.** `rollback.abandon` (for `--abandon-rollback`) refuses while anyone holds the apply flock, then moves every intent, unparseable ones included, to `apply/abandoned/`. Every intent write creates that directory first, so on the full disk that left an intent pending the move is only renames (a read-only disk moves nothing). The CLI releases the config lock while its y/N prompt waits and retakes it before the move, which it skips when the pending intents changed meanwhile. It leaves `apply/inflight.json` alone: an interrupted apply's file can still be recovered (by the next plugin change, apply, `--status` or launcher pass), which can read the rejection again and write a new intent, so the CLI says so when one remains, and the abandon may need a second run once `apply --status` has settled the file.

### The apply verb (host)

`cogbox plugin apply` (`zig/src/plugin/apply.zig`) builds the runner the next boot would build from the committed plugin state and decides whether it can be loaded into the running guest. It reports one outcome: a JSON line with `--json` (`{"apply":{"gen","op","result","reason","detail","overridable","plan","forced","rollback","runner","toplevel","units","rolled_back_guest","cap","base_id","built_id"}}`, every key present, every value an enumerated token, a host-derived store path or snapshot id, or a unit name that exists as a unit file in T or P), written to `apply/last.json` first. Exit status: 0 for a classified outcome, except that without `--json` a `rejected` one exits 1 (as an inline apply's rejection does); 78 when a rollback that cannot finish blocks the apply, or when its own rollback stays pending (the report says so); 64 for a usage error (an `apply` command line that does not parse is refused before any lock is opened or waited for), and for `--force` with `--json` or without stdin and stderr both on a terminal (the dispatcher refuses those before any lock too; `--force-plan` is a plain run); `--force` exits 1 when its question is declined or not answered, when the plan cannot be listed, and after three changed or expired plans, and otherwise as its last apply did, so a refusal it does not ask about (a never-overridable reason) exits 0 with nothing applied anyway ([below](#apply-anyway-host)); 128 + the signal on the terminate path (143 when the whole-verb timer ends the guest phase).

The CLI takes the instance config lock with a bound (300 s for `apply`; on expiry the verb answers `failed/busy`), installs the verb's signal handlers first (TERM, INT and HUP set a terminate flag, USR1 a supersede flag; SIGPIPE is ignored), and hands the verb the config lock's descriptor and that of the apply flock (`<config>/.locks/<name>.apply.lock`, created like the config lock). Then:

1. **Preflight**, under the config lock. The apply flock by `LOCK_NB` (held: `failed/busy`); `COGBOX_LIVE_APPLY=0` answers `restart_required/disabled`; a build unit an earlier apply left running is stopped when `apply/active` still names it and its InvocationID matches; `apply/active` = `{pid, starttime, unit, invocation, op, gen, scratch_id, phase, deadline}` (the deadline in CLOCK_BOOTTIME seconds, preflight's start + 445 s, kept when S is named). An `apply/inflight.json` that survives recovery answers `failed/busy` with `inflight_unresolved`; a pending rollback intent is finished (one that cannot finish: exit 78). Then, in order: `not_running`; `booted-runner` with three lines (else `no_boot_record`) under the current `COGBOX_FLAKE_SOURCE#COGBOX_REEXEC_PACKAGE` key (else `base_changed`); `apply/base` naming a complete snapshot whose comp equals `$RUNTIME/live-runner`'s when this boot has one (its fourth line is the boot nonce, so one from an earlier boot of the runtime dir is ignored), else booted-runner's line 3, strictly the one (else `no_boot_record`); the base's composition consistency (`composition_stale`); with no plugins, an edited `flake/flake.nix` (`customized_flake`: the next boot would re-execute from it); `qemu.start` (`booting`; the [plan store](#apply-anyway-host) is pruned once it reads); hosted with network `none` (`air_gapped`); `MemAvailable` against `COGBOX_APPLY_MIN_AVAILABLE_MB` (2048) and the free space under the instance config dir against `COGBOX_APPLY_MIN_FREE_MB` (64) (`insufficient_memory`, `insufficient_disk`); the containment mode (`no_containment`, below); `nix hash path` of the user flake (30 s) against the composition lock's `user` narHash (`user_flake_changed`); the scratch snapshot S (`failed/snapshot`; `apply/active` names it before the config lock is released, and the snapshot GC runs only under that lock) and its composition consistency; the rollback scopes, against B and against K (else B); and, with `--force-plan`, the binding of the stored plan (`plan_expired`). The config lock is then released and `apply/active` moves to `phase: build`, from which a plugin change supersedes the apply.
2. **Build**, bounded by `COGBOX_APPLY_BUILD_TIMEOUT` (1800 s) shared by every stage, after the trash is emptied (30 s, ended by either flag). Stage (a) is `nix eval --raw` of the configuration's `config.microvm.declaredRunner.drvPath` with `--override-input userExtensions path:<S>/composition`, `--override-input userExtensions/user/nixpkgs`, `--no-write-lock-file` and the re-exec's substituter options; stage (b) is `nix build '<drv>^out' --out-link gcroots/applied/<G> --max-jobs 1 --option cores 1`. With no plugins the target is `COGBOX_BASE_RUNNER` and nothing builds. Output goes to `apply/<G>.build.log` (64 KiB; the 16 newest are kept), which `apply --log G` prints (the last 32 KiB, ANSI stripped). Containment follows Nix's own store selection: a daemon client (`cap: none`) runs nix as a direct child; a local store needs root and systemd and runs each stage in `systemd-run --unit=cogbox-apply-build-<12 hex of sha256(icd)> --service-type=exec --collect --wait --pipe -p RuntimeMaxSec=<left> -p KillMode=control-group -p MemoryMax=<MemAvailable - 512 MiB> -p OOMScoreAdjust=1000` (`cap: unit`), with only `PATH`, `HOME` and a few nix/TLS variables passed by name, never a value and never `NIX_CONFIG`. Every 10 s the instance must still run the same boot (`superseded` once it stopped or runs another; a `qemu.start` that cannot be read for a moment ends nothing), as must every guest hop below. On the terminate flag before `start` the verb stops a build unit a stage left running (`systemctl stop --no-block`, 10 s, run through the flag) and exits 128 + the signal; `apply/active` is removed only once that stop was accepted, and otherwise stays as the record of the unit and its InvocationID that the next preflight, `apply --cancel`, `cogbox delete` and the launcher stop it by (its holder is dead, so no gate waits on it). Every child stays in the verb's process group, so a group signal (a terminal's Ctrl-C, the local backend's SIGTERM to the group) can end a child before the verb's loop sees the flag: a child that fails while the terminate flag is set counts as stopped by it, never as its own failure.
3. **Classification.** `eval_error` needs positive evidence: stage (a) exited 1 without a signal or a unit Result of oom-kill, timeout or signal; its stderr (whole, not truncated) holds `error:` and an evaluation marker and no infrastructure marker (no space, bad_alloc, out of memory, daemon EOF, socket, connection reset, interrupted, timed out, download or HTTP errors, a NAR hash mismatch, `Cannot build '`); and a second stage (a) fails the same way with the same first `error:` line that carries a message. It flips `apply/active` to `phase: record` at once and writes the rollback intent against K, else B. Otherwise a NAR hash mismatch is `failed/inputs_changed`, a fetch failure `failed/build_inputs_uncached`, a timeout `failed/build_timeout`, the unit's OOM kill `restart_required/insufficient_memory`, the whole-verb timer `failed/timeout`, anything else `failed/build`.
4. **Tier 1**: `unitplan.bootShape` of the booted runner against R (`boot_shape`, `kernel_modules`, `fstab`, `init_interface`, never overridable).
5. **Tier 2**: `settled --wait 25` hops for at most 180 s (`booting`; a missing helper, exit 126/127, is `no_helper`), then `plan T` (90 s; a busy generation no host verb tracks is aborted and waited for, at most 420 s, then planned once more, else `failed/busy`; `guest_tainted`). The guest must have booted B's system (`no_boot_record`) and run P, live-runner's system else B's (`foreign_system`); R equal to P's runner is `already_live`; a fallback store is `store_fallback`; dry-activate's refusals are `pre_switch_check`, `init_interface` and `failed/switch_locked`. The host plan over P's and T's unit files and the mounts of their `etc/fstab` (`unitplan.planHost`) gets the guest's data merged in, which refuses, and narrows only for the guest's own units: every name is intersected with the T/P unit files and fstab mounts; a reply with no `active` unit is malformed (`failed/plan`); an `inactive` claim drops only that unit's stop, restart or reload (never a start, never a template's other instances); dry-activate's actions are added, and the induced starts as propagated starts; the runtime reverse edges join the graph. The closure's seeds are the plan's units, the hidden stops of the `X-StopOnReconfiguration` targets, the hidden start of every target the guest runs (switch-to-configuration starts every active target after the daemon-reload, which starts every unit they reach that is not running, though neither the plan nor dry-activate names it: a `docker.service` an active target newly wants, a failed mount) and the restart of `sysinit-reactivation.target`. A start reached over an edge is no hazard when the guest runs the unit (whatever its class, `user@<uid>` included; the walk goes on through it, but not over its `OnFailure=`/`OnSuccess=`, which a no-op start never fires), when it is a once-marked boot-only unit whose marker the guest holds and whose T unit keeps the marker condition (a boot unit that failed or never ran has no marker: class A), or when no file defines it and the guest cannot load it; any other start, stop, restart or reload is classed as listed (systemd-logind is disruptive only when it would stop or restart, and its start is never a hazard; a stop or restart of `cogbox-reply-route`, which deletes the reply table, is `restart_only_units` however it is reached, and a propagated start or reload of it is no hazard; only `podman.service`, `podman.socket` and `podman-restart.service` are podman's, a plugin's `podman-<name>` container unit is its own, and a start of an existing `podman.service` reached over an edge, from a plugin unit that `Requires=` it, is never a hazard: the socket-activated API service exits after 5 s idle, so whether the guest runs it is chance, and it owns no container). Units are tracked by name, so one template instance never stands for another. The user units (`etc/systemd/user`) the user pass would stop, restart, reload or leave stale are `restart_only_units` (`nixos-activation.service` aside; a unit T adds is allowed): neither the plan nor dry-activate sees that pass. Residual: the user pass's second (migration) pass restarts, or starts, a unit T adds that a user's manager already runs from another unit directory (`$XDG_DATA_HOME/systemd/user` and the like, or `~/.config/systemd/user` once its copy is gone), and that restart is not refused. So is every entry of `etc/systemd/system-generators` and `etc/systemd/user-generators` that T adds, removes or retargets (compared by what each entry resolves to, so a rebuilt directory with the same entries is no change), named `system-generators/<name>` or `user-generators/<name>`: the daemon-reload runs T's generators, and the switch's start of the active targets starts what they write under `/run/systemd/generator`, which no unit directory the plan reads holds and dry-activate never runs (a plugin's `zramSwap` adds `zram-generator`, whose `dev-zram0.swap` the start of `swap.target` would swap on). `etc/fstab` is pinned by tier 1, so the fstab generator's output is the boot's. The verdict follows. A refusal is `restart_required/<reason>` with its units as `detail` (a template instance that only the guest's data named, an induced start or a runtime edge's unit, is shown as its template: guest data may refuse, but its text never reaches the report), and when it has a class B, C or D part a `plan` `{id, boot_id, comp, P, T, units: [{unit, action, why, class}], repair, reexec}`, whose id is the first 16 hex of the sha256 of its canonical JSON; an overridable refusal's plan is stored in `apply/plans/`, and under `--force-plan` this re-plan decides what is forced ([below](#apply-anyway-host)). A clean plan goes to the guest phase, after the supersede flag and the free-disk floor are checked once more.
6. **Guest phase** (`runGuestPhase`). `apply/active` flips to `phase: guest` (deadline W + 1020 s); from here a supersede request is ignored. Before every `start` attempt the verb writes `apply/inflight.json` = `{G, op, scratch_id, base_id, nonce, boot_id, host_boot, R, key, T, P, scope, expires_at, hops: {streak, confirm_failed, rfails, seen}, forced}` (atomically; `expires_at` is CLOCK_BOOTTIME seconds, the attempt's time + 45 + W + 390, so a wall-clock step never moves it), then sends `start G T REGINFO --prev P --boot-id ID --bound S --window W` (REGINFO is the `regInfo=` of R's `bin/microvm-run`; S is 840 s and W = S + 120, with S from `COGBOX_APPLY_SWITCH_TIMEOUT`, clamped to the helper's 60 to 3600 s, so every leg derived from W follows it; a forced run appends `--force-units -`, the list on the hop's stdin, when its plan stops, starts or restarts a unit, and `--repair cogbox-reply-route.service` when its plan has one). Attempts repeat within the 45 s start leg; a refusal (`busy`, `guest_tainted`, `superseded`, `stale_boot`, `error`) means G was not created, but after an attempt lost in transport G is first tombstoned with `abort` so a late `start` answers stale. The poll then long-polls `status G --wait 25` until G is terminal, bounded at the first attempt + 45 + W + 390 s (1395 s at the defaults), and confirms a `switched` G with `confirm G` on a fresh connection that, with the cogbox key, reads no ssh config (`-F /dev/null`); every hop carries `ControlMaster=no`, `ControlPath=none` and `ControlPersist=no`. After three failed hops in a row only `status` polls go out until one reads the guest again. A G the guest still does not know after the start leg is tombstoned (`failed/guest_refused`, `not_started`).
   - **Hop evidence** (persisted in `inflight.json` whenever it changes): a failed hop increments `streak` and a failed confirm also sets the sticky `confirm_failed`; a successful hop resets `streak` only when it reads G in a state other than `reverting`, `reverted` or `revert_failed`, so the hop that observes a dead-man revert never erases the evidence for it; `seen` keeps the recorded verdict or cause (or `confirmed`) a hop reads, and once it is set the streak no longer moves. A hop cut short by a terminate signal, the whole-verb timer, the poll's end or a stopped instance is not evidence, and neither is a failed SIGINT `abort` (a second Ctrl-C reaches its ssh too).
   - **Judgement**: `confirmed` is `applied`, or `applied_with_failures` after a switch exit of 2 or 4 (the failed units in `units`); a no-op `refused` is `restart_required/store_fallback`, `pre_switch_check` or `init_interface`, `failed/switch_locked`, `failed/busy` (`busy_gc`), else `failed/guest_refused` with the helper's refusal token in `detail` (`store_path_hidden`, `store_whiteout`, `register_failed`, `run_failed`, `start_failed`, `deadman_failed`; any other word a guest prints there reads `invalid`, so the guest never chooses report text); `stale` is `unknown`. A recorded verdict or cause decides in any state: `breaks_base`, `activation_failed`, `activation_hang` and `unit_hang` are `rejected` (rolled back); a `dead-man` revert is `rejected/unreachable` only with hop evidence (a streak of at least 3 or a failed confirm; `recovered` once the guest is seen reverted, else `unrecovered`), else `undone/host_lost`; `aborted` (`during_activation` when the switch was running), `stop_hang`, `switch_timeout`, `unplanned_disruption` and `forced_unit_failed` are `undone`; any other switch exit is `undone/switch_failed` (`exit_<n>`). A rejecting verdict becomes the rollback intent (target B, the live scope) as soon as a hop reads it, before `inflight.json` records it in `seen` (a recoverer does the same), and the poll goes on to a terminal state for `rolled_back_guest` (false and `revert_failed` when the guest's revert failed). Unit names in `detail` and `units` are reported only when T's or P's unit directory names them exactly (a file, a drop-in directory, a `.wants`/`.requires`/`.upholds` link); a template instance neither names is reported as its template, since any instance of an existing template is a valid name and its instance text would be the guest's own. For an outcome other than applied, while the poll's bound leaves a hop's time, `log G` is kept in `apply/<G>.guest.log`, which nothing exports.
   - **The poll ends early** when the instance stops or relaunches (checked at every iteration): a verdict already seen decides, else `unknown`. When the bound passes, the expiry rule applies, only while the same boot runs: `rejected/unreachable` (`unrecovered`, intent written) with hop evidence, else `unknown`. A `qemu.start` that cannot be read on a running instance ends nothing (every hop carries the boot id, so a guest that booted again answers `stale_boot`); a poll whose bound passes while it still cannot be read is `unknown` and keeps `inflight.json`, with its hop evidence, for a recoverer.
   - **Signals**: the TERM, INT and HUP handlers set the terminate flag and USR1 the supersede flag (ignored from the flip on). From `start` until the step-10 lock is held, SIGTERM (and the whole-verb timer) ends the verb at once with exit 143, leaving `inflight.json` for a recoverer and printing no report; SIGINT and SIGHUP first send one `abort G` (15 s; a no-op once a verdict is recorded), persist what it read in `seen`, and exit 130 or 129.
7. **Record** (step 10), under the config lock retaken with a 300 s bound that the terminate flag and the whole-verb timer interrupt (from `start` on, that takes the terminate path above); from the moment the lock is held until the report the flag is ignored. Every rollback runs from its intent (`rollback.finishPending`; target B for a live rejection, K else B for an eval_error; the report's `rollback` object carries `status`, `target` and `target_id`, `pending` when the lock could not be had). The other records require the boot preflight saw: `applied`, `applied_with_failures` and `already_live` get the confirmed record (R and its key into S's `meta.json`, `apply/base` := S, `apply/built` unlinked, `$RUNTIME/live-runner`, and `runner.path` when the key is the current one and `plugins-flake/` still equals S, clearing `composition.lock.prev` and the repin verdict); `restart_required`, `failed` and `undone` after a successful stage (a) set `apply/built` := S, and the restart_required reasons that record R also write it into S's `meta.json` and `runner.path` the same way. `rejected`, `superseded` and `unknown` never set K. A build-phase run that waits for the lock only to set K gives the wait up to a plugin change's supersede request and ends `superseded` (a free lock is still taken). When K := S is not made (the lock wait ran out or gave way, the boot cannot be told, or `apply/built` could not be written), the older K, else B, stays the `eval_error` target, so a later `eval_error` in the same boot rolls this change back too; the guest does not run it, as with a commit no apply reached. A confirmed generation whose record could not get the lock, whose boot cannot be told (`qemu.start` unreadable on a running instance), or whose record fails part-way (ENOSPC, EIO) keeps `inflight.json`, whose recovery records it. A record that fails part-way also unlinks `apply/base` and `apply/built`, which lack the change the guest now runs, so no rollback can target them and applies answer `no_boot_record` until the record is made or a relaunch re-promotes the base. Then `inflight.json` and `apply/active` are removed, both locks are released, and the report is printed last.

Every child (nix, ssh, systemd-run, systemctl) is forked from the verb's main thread and makes only raw syscalls before `execve` (`PR_SET_PDEATHSIG=SIGKILL`, a `getppid` re-check, SIGPIPE back to default, `dup2`; stdin is /dev/null, or a memfd the verb filled before the fork for a hop that sends bytes), stays in the verb's process group, and is waited for through a pidfd in a 250 ms poll loop that also sees the flags, the bound and the watch. Guest hops add `BatchMode=yes`, `ConnectTimeout=10`, `ServerAliveInterval=15`, `ServerAliveCountMax=4`, `ControlMaster=no`, `ControlPath=none` and `ControlPersist=no`, are killed at 45 s (90 s for `plan`), and their replies are capped. The whole verb is bounded by `COGBOX_APPLY_TIMEOUT` (5340 s from process start).

**Interrupted applies.** `apply`, `apply --status` and `apply --cancel` recover an `inflight.json` its verb left (killed, or on its terminate path) once they hold the apply flock (`recoverInflight`). A stopped or relaunched instance (not running, another `qemu.start`, or another host boot id) resolves as `unknown` (`relaunched`), or as the rollback of an intent the dead verb wrote, or of a rejecting verdict `seen` records whose intent never became durable; a running one whose `qemu.start` or host boot id cannot be read leaves the file. On the same boot one `status G` hop (45 s) reads the guest: a rejecting verdict or cause, in any state, becomes an intent at once and is rolled back (a `dead-man` revert only with the persisted hop evidence); `confirmed` gets the confirmed record (`runner.path` only under the stored key's own image, else it is removed; a record that fails leaves the file); other verdicts and causes are `undone/<cause>` (K := S). A verdict-less G is aborted (a no-op once a verdict is recorded) and waited for at most 60 s; still verdict-less, the file stays. An unknown G is aborted too, which tombstones it, so a `start` the dead verb left in flight answers stale. A failed hop increments `rfails` (a successful one resets it; `cogbox stop`'s 3 s hop, `short_hop`, never touches it; no recoverer touches `streak`); before `expires_at`, or past it while `rfails` is below 3, the file stays, and once three full-length hops in a row have failed past it the persisted evidence settles it: `seen` first (`confirmed` is recorded, a non-rejecting cause is `undone`, a rejecting verdict rolled back), then hop evidence (`rejected/unreachable`, `unrecovered`), else `unknown`. So a confirmed or aborted change is never rolled back on missing evidence. A recoverer without the config lock acts only on a rejecting verdict, which it writes as an intent, and leaves the file. Every resolution is written to `last.json` with the op from `inflight.json`; a recovery under the config lock runs the rollback itself, so `last.json` carries its `rollback` object. At most 45 + 60 s of hops, plus the record.

`apply --status` (config lock bounded at 15 s; without it, it only reports) recovers and finishes pending work when it can also take the apply flock, then reports `{"status":{in_flight, in_flight_reason, last, base_id, built_id, rollbacks, records_id, rollback_pending}}`. It prints the stamped `could not be finished` line only for an intent its own finish left; one it could not try to finish (a live apply or a plugin change holds the apply flock and may be finishing it) is only counted in `rollback_pending`. `apply --cancel` signals the holder `apply/active` names through a pidfd after a starttime check (SIGTERM, at most 30 s; with the config lock then SIGKILL, at most 10 s; without it never a SIGKILL, and a holder that outlives the SIGTERM, one inside its step-10 section, answers `pending` and exits on its flag). With `--op RUN` it acts only on a holder whose `apply/active` carries that op: a live holder of another run gets no signal, its flock, build unit and `inflight.json` are left alone, and the answer is `none`. Otherwise it stops the build unit on an InvocationID match, by the `apply/active` it reads once it holds the apply flock (the holder may have rewritten it for a later stage before it ended), keeping `apply/active` when the stop cannot be confirmed, and finishes pending work. `--status`, `--cancel`, the apply's preflight, the plugin subcommands' gate and the launcher's preboot run one rollback finish per call: the recovery's, when it rolled back. `apply --abandon-rollback` moves every pending intent aside. Plugin subcommands other than `apply` finish a pending rollback before they read config.json; `add`, `del`, `update` and `reconcile` exit 78 when one cannot finish.

### Apply anyway (host)

An overridable refusal (`disruptive_units`, `network_config` or `systemd_reexec`, with no never-overridable reason beside it) can be forced by a later run bound to its plan.

- **Plan store.** Step 5 writes every offered plan to `apply/plans/<id>.json` = `{plan, reason, created, nonce, host_boot, gen}`: the plan as reported, its own overridable reason, `created` in CLOCK_BOOTTIME seconds, the boot's `qemu.start` and host boot id, and the run that planned it. It is a new file (tmp, fsync, rename) under the apply flock, owned by the invoking user under sudo; a `plans` that is not a real directory is refused. A plan that cannot be stored (or whose host boot id cannot be read), or whose force list exceeds what the guest helper takes (more than 256 names, more than 64 KiB, a name outside its charset), or that names a unit outside that charset in any unit or `why` (`propagated:<edge>:<from>` names a unit of T or P, which plugin code chooses, and the listing a person agrees to must show only what it says), is not offered: `overridable: false`, `plan: null`, the units still in `detail`. A mixed refusal's plan is listed, never stored. Each apply's preflight, and nothing else, prunes the store: leftover tmp names, files that do not parse or validate, plans 30 minutes old or more, from the future, or of another `qemu.start` or host boot, then all but the 16 newest, never counting the plan the run's own `--force-plan` names (its binding reads it next). Other names are left alone; `cogbox delete` removes them with the instance.
- **Binding.** With `--force-plan ID` the last preflight check (under the config lock, after the rollback scopes, so `disabled`, `not_running`, the identity checks, `booting`, memory, disk and the user flake answer first) admits the run only when `apply/plans/ID.json` exists and parses; its file name, its `plan.id` and the id its content hashes to are all ID (a hand-edited unit list cannot keep the id); its reason is overridable; its force list fits the helper; its `qemu.start` and host boot id are this boot's; its `comp` is S's; and it is less than 1800 s old. Anything else is `restart_required/plan_expired`: no plan, no K, no R, nothing built, the guest never asked. The admission (`"event":"force","phase":"admitted"`, the invoking uid and euid, G, the op, the plan, its reason and the units it would relax) is appended to `apply/audit.log` under the config lock, before anything is forced.
- **Re-plan.** The admitted run builds and plans as any other, and only the same id is forced. A refusal that is never overridable (a mixed one included) is reported unchanged; an overridable one with another id is `restart_required/plan_changed`, never overridable itself, its new plan stored and reported and the guest untouched (K := S, no R); a re-plan that is clean applies as a plain run, nothing forced. Tier 1 and the guest's no-op refusals answer before the re-plan, untouched by force.
- **Forced start.** The `start` hop appends `--force-units -` and puts the force list, one name per line, on the hop's stdin: a memfd filled before the fork, fresh for every attempt, so a retry resends the same bytes (a pipe would need a writer in the poll loop, and a full list is a default pipe's whole capacity). The list is the names of the units the plan stops, starts or restarts, sorted and unique; a unit it only reloads and the repair unit are left out. The guest exempts a listed unit from every comparison whatever the plan does to it, while a reload keeps a unit's InvocationID and its running state, so a reload-only unit (networkd for a `.network` change) needs no exemption and stays held to all of them: a restart or stop of it during the switch is still `unplanned_disruption`. It appends `--repair cogbox-reply-route.service` when the plan has a class C unit or `firewall.service`. A plan with nothing to relax (it only reloads units or re-executes systemd) sends no `--force-units` (the helper refuses an empty list), and a re-exec-only plan neither option. The guest leaves the listed and repair units out of every post-check comparison (state, InvocationID, the switch's failed list) and journals them; the base checks are never relaxed, and on a switch exit of 4 a listed unit that failed while the base stayed healthy is `undone/forced_unit_failed`. Everything else is judged as in a plain run: a forced rejection is rolled back, and unlinks K, like any live rejection.
- **Records.** `inflight.json` carries `forced: {plan, units}` from the first forced `start` attempt, and so do the report and `last.json`, a recovered run's included. It is there whether or not a list was sent: a forced run that relaxes no unit (it only reloads units or re-executes systemd, or both) reports `units: []`, so an empty list never says that systemd was re-executed (the plan's `reexec` does). `forced` is `null` for every run that attempted no forced `start`: `plan_expired`, `plan_changed`, a never-overridable or clean re-plan, and a forced run that ended before its first `start`. A completion line (`"phase":"done"`, `forced`: whether a forced `start` was attempted, the units it relaxed, the result and reason, `recovered`) follows in `apply/audit.log` when the admitted run ends without keeping `inflight.json`, written under the config lock or a `LOCK_NB` try of it, or else by the recoverer that resolves the file, once. An admitted run keeps only its admission line when it finds that lock busy at its end, when a signal ends it before its first `start` (the terminate path exits with nothing recorded), when its re-plan was clean and it kept `inflight.json` (the recoverer writes a line only for a file that carries `forced`), and when the process that removes `inflight.json` (the run or its recoverer) dies before its append (a lost line rather than a doubled one).
- **`--force`.** The dispatcher refuses it (64), before any lock is opened or waited for, with `--json` (one report per invocation, and `--force` runs several applies) or unless stdin and stderr are both terminals: the plan is shown on stderr and the answer read from stdin, and stdin alone would let `2>/dev/null` hide the list being agreed to. Round 0 is a plain apply (its human line drops the Apply anyway hint). An overridable outcome is listed on stderr (each unit's action, why and class, what a stop or restart of docker and a restart of sshd or resolved end, in the control plane's words, and which checks force relaxes) and asked about, `[y/N]`, yes only for an answer that starts with y, never through `confirm()`, which says yes off a terminal. A listing or question that cannot be written is not asked about (no). Right before each question is written, the terminal's unread input (`TCIFLUSH`) and whatever the reader holds past the last answer are discarded, so a line typed ahead during a round, or before a changed plan was listed, never answers it, while an answer typed on seeing the question is never lost. Nothing is held while the question waits: round 0 released both locks and cleared `apply/active`, and nothing reached the guest, so TERM, INT and HUP have their default action there. A yes reinstalls the verb's handlers, restarts the whole-verb timer (it bounds one apply, not the reading), retakes the config lock with the dispatcher's 300 s bound (the timer counts that wait, as the dispatcher's does from process start), and runs the apply with `--force-plan` of the plan shown; a `plan_changed` is listed and asked about again, at most three forced runs, then nothing is applied anyway. A `plan_expired` from a forced run (a plugin change, a restart, or the plan's half hour while the question waited) is planned again by a plain apply, as round 0 was, under the same retaken lock and restarted timer, and the plan it offers is asked about next (listed as changed when its id differs); after the third forced run nothing is planned again. A supersede request a round got after its last check is dropped before the next round, so it cannot end that round's build at once (its plugin change is caught by the binding). A decline, EOF and that abort exit 1; otherwise the last run's exit code. Off a terminal, the human line of an overridable refusal, and of a `plan_changed` with its new plan, lists the whole plan (every unit with its action, why and class, the re-exec, the repair) before the `--force-plan` line that names its id, the id's only mention: the units after the reason are that reason's alone, so a disruptive plan that also reloads the network or re-executes systemd would otherwise show part of what forcing its id does. A plan that cannot be listed gets neither hint. `add`, `update` and `del` never ask: on a terminal (stdin and stderr) their inline hint names `cogbox plugin apply --force`, the first eight units, the re-exec and the repair; off one, where `--force` refuses, it lists the whole plan the same way and only then the `--force-plan` line with its id.

### On-disk state

Under the instance config dir `<icd>` (everything the apply writes there is written as a new file, by tmp + rename, and chowned to the invoking user under sudo):

| Path | What |
|---|---|
| `apply/snap/<id>/` | a snapshot: `composition/{flake.nix,flake.lock}` (byte copies), `state.json`, `src/` (hard links of `plugin-sources/`), `meta.json` last (`{id, comp, runner, key}`); without `meta.json` it is incomplete and never used |
| `apply/base`, `apply/built` | the role symlinks: B (what the guest runs) and K (the last state that evaluated, after a `restart_required`, `undone` or `failed` apply) |
| `apply/booting`, `apply/pin/<id>/`, `apply/trash/` | the launcher's latest boot snapshot id, its composition pins, and what the GC moved out (emptied by an init-only pass and by an apply's build phase) |
| `apply/active` | the running apply: `{pid, starttime, unit, invocation, op, gen, scratch_id, phase, deadline}` (the deadline in CLOCK_BOOTTIME seconds); the gate and `--cancel` read it |
| `apply/inflight.json` | the guest phase's durable state, written before every `start` and removed once the outcome is recorded, or left for a recoverer |
| `apply/rollback/<G>.intent` | a pending rollback (`{G, op, reason, target, target_id, scope}`); at most one exists. `apply/abandoned/` holds the ones `--abandon-rollback` moved aside |
| `apply/rollbacks.jsonl`, `apply/rollbacks.id`, `apply/audit.log` | the rollback records (the last 64), the records file's id, and the audit trail (also every Apply anyway admission and end, `"event":"force"`) |
| `apply/plans/<id>.json` | an offered Apply anyway plan, `{plan, reason, created, nonce, host_boot, gen}`; written at step 5, read by the binding, pruned by each apply's preflight (older than 30 minutes, another boot, unusable, past the 16 newest but the one its `--force-plan` names) |
| `apply/last.json` | the last report, written before it is printed |
| `apply/<G>.build.log`, `apply/<G>.guest.log` | a generation's build output (64 KiB; `apply --log G`) and the guest's log of it (never exported) |
| `gcroots/booted`, `gcroots/applied/<G>` | the booted runner and every runner an apply built this boot (cleared at the next launch) |
| `runner.path` | the next boot's fast-path record: key, runner, comp |

In the runtime dir: `booted-runner` (key, runner, comp of the boot) and `live-runner` (key, runner, comp and boot nonce of the last confirmed apply of this boot; it never outlives its boot: the launcher's daemon pass recreates the runtime dir under the lifetime lock before QEMU starts, and the nonce line would keep any copy that survived from matching a later boot).

`checks.cogbox-vm` phase LA drives the whole mechanism in a real guest: live add, update and removal (a package, an `/etc` file, a service, a skill) with a tmux session and an ssh session held open; the fast-path restart; the rollbacks of an add (`activation_hang`), an update (`unit_hang`), a removal (the plugin reinserted, its deny back, its allow not) and an `eval_error` (back to K); a lockout only a fresh connection sees (`unreachable`, with the user's `ControlMaster auto`); a restart right after a rejection; supersession by a plugin change, and a change that gives up waiting (exit 69); `cogbox init` on a running instance; the never-overridable `restart_only_units` and `skipped_units`; a failed boot snapshot (`no_boot_record`); and planted intents finished by the launcher, by the fail-closed tier, and one that cannot finish (exit 78, then `--abandon-rollback`). Its Apply anyway legs: a docker setting and a change to the uplink's `.network` file, added inline, are planned, stored and hinted at but not applied; `--force` exits 64 without a terminal and with `--json`; an unknown plan id is `plan_expired`, and the stored id once the guest's docker was stopped is `plan_changed` (the new plan stored, the guest untouched); with docker running again the same id applies (docker.service stopped and docker.socket restarted, both relaxed; networkd reloaded but not relaxed, so every post-check still holds it; the reply route repaired; the relaxed units, without networkd, in the guest's journal; the admission and the end in `apply/audit.log`), and `--force` on a terminal lists the plan, holds neither lock while it asks and applies it on `y`; a forced sshd restart that denies root passes the guest's own checks but shuts out every fresh connection, the host's hops included, while the user's `ControlMaster auto` master survives (`unreachable`, rolled back), and that live rejection unlinks K, so the `eval_error` that follows rolls back to B; a forced sshd whose config does not load is `breaks_base` and rolled back (force never relaxes a base check); the hosted guest applies a forced `.network` change (`network_config`) with the repair and nothing relaxed (`forced.units` is `[]`, the guest's journal names the repair alone); and the never-overridable results offer no plan and no hint. It also checks the host's unit plan against the guest's own `switch-to-configuration dry-activate` for every composition it applies and for three single changes (a docker setting, nftables, the uplink's `.network` file): whatever dry-activate would stop, start, restart, reload or leave alone, the plan does too, and a unit only the plan lists is new or not active in the guest. The hidden `cogbox __unitplan P T` prints the plan for that comparison (`<action> <unit> <why>`, `skip <unit>`, `reexec yes|no`). Its test plugins are in `tests/fixtures/live-apply`, and `flake.nix` pre-builds the runner of every composition it applies, because the test machine is offline. Residuals, legs of the design's test plan that no check drives in a real guest yet: `del X` then `add X` at the same pin, a reboot and a rejected later change leaving X's rules untouched; a source restore that hits ENOSPC with a fail-closed tier that fails too (exit 78, and the rejected change never boots; the exit-78 leg uses a read-only config directory); a boot snapshot that fails on a full disk (the leg makes `cp -al` fail across a tmpfs instead); and of Apply anyway, a `systemd_reexec` plan (the InvocationIDs are inferred to survive a re-exec; if one did not, the result would be `undone/unplanned_disruption`, never a rollback), a forced nftables ruleset change (enabling nftables changes the initrd, so it is never live on a VM guest, and a ruleset change needs an nftables the boot already enabled), a forced docker change on the hosted guest, and the decline, the three-round abort and the re-plan after an expired plan of `--force` (unit-tested).

### Plugin changes, stop, delete and the launcher

- **The apply gate.** `add`, `update`, `del` and `reconcile` take the apply flock (`<config>/.locks/<name>.apply.lock`) before the instance config lock and keep it until they exit, so a plugin change and an apply are serialized and a rollback always finds the plugin state its apply started from. The global lock order is apply flock, then config lock; every party that holds the config lock touches the flock only by `LOCK_NB`. Free, the flock is taken at once. Held, the gate re-reads `apply/active` every second and its bound follows the latest read: no live apply named (another plugin change holds the flock) waits without a bound, as the config lock always has; `preflight` waits until its deadline; `build` sends SIGUSR1 once per holder (pid and starttime, through a pidfd), which ends that apply `superseded` with its build unit stopped and the guest untouched, then waits at most 60 s; `guest` or `record` prints `cogbox plugin: waiting for the live apply of generation G to finish (at most N s)`, reprints it with the time left every 60 s, and waits until the deadline. Every wait behind a live apply is capped at `COGBOX_APPLY_WAIT_MAX` (1200 s; the control plane is to pass 90 s once it drives live apply), from the first read that named one. When a bound expires the change exits 69 with `cogbox plugin: error: busy: a live apply is finishing (generation G); try again in a few minutes`, having read and written nothing. Past the gate and the config lock, an `inflight.json` whose verb died is recovered (at most 115 s; a rejection it still holds is rolled back before the change commits, and one that cannot be resolved exits 69 the same way), then a pending rollback is finished (sweeping intent tmp names, since the gate holds the flock), then config.json is read.
- **Inline apply.** After a committed `add`, `del` or `update` on a running instance, the verb applies the change live when `--apply` was passed, or, without `--no-apply`, when stderr is a terminal and `COGBOX_ENVIRONMENT` is not `cogworx`; never on a non-terminal without `--apply`, and never with `COGBOX_LIVE_APPLY=0`. The apply runs in the same process under the gate's flock and the mutation's config lock (its preflight keeps both), with its whole-verb timer started there. It prints the outcome: loaded, `'X' was not applied and has been rolled back: <reason>. Build log: cogbox plugin apply --log G` (exit 1), or why it was not loaded live with the restart hint (and, for an overridable refusal, `Or run 'cogbox plugin apply --force' to apply it now anyway; it would: ...` when stdin and stderr are terminals, else the whole plan and the `--force-plan` line, as under `--force` above). A rejection whose rollback is not `done` says what happened instead (`apply.rollbackSentence`, which `cogbox plugin apply`'s own line shares, so one report reads the same both ways): the fail-closed tier removed the plugins the change added or updated (a del's stay removed), the rollback is pending for the next plugin command or start, or, with exit 78, it could not be finished; a report without a rollback status reads as pending, never as rolled back. A deferred change prints `Run 'cogbox plugin apply' to load it live, or restart the instance`; a stopped instance prints that the change takes effect at the next start.
- **`cogbox stop`**, before it signals the launcher and without the config lock: when `apply/active` or `inflight.json` exists and `--force` is not given, SIGTERM to the live holder through a pidfd and a 2 s grace (never a SIGKILL; a holder still alive leaves `inflight.json` for the next recoverer); with the holder gone and the apply flock free by `LOCK_NB`, one `status G` hop under a 3 s kill in the lock-free recoverer's form: a rejecting verdict becomes the rollback intent the next launch finishes, nothing else is settled, and the hop never counts toward `rfails`. At most 5 s in all, inside the 10 s between stop's 65 s guest wait and the GCE unit's `TimeoutStopSec=75s`.
- **`cogbox delete`** stops the build unit `apply/active` records (on an InvocationID match) before it removes the instance; the apply's own watch then ends it `superseded`.
- **The launcher.** Every pass runs `cogbox __plugin-apply-preboot <icd> --runtime <runtime> [--name NAME] [--init-only]` right after the config lock, under the inherited lock (it never takes the lock), bounded from outside at 360 s (its legs: holder 40, unit stop 20, rollback finish 240, trash 30). On a stopped instance it signals the apply holder (SIGTERM, at most 30 s, then SIGKILL, at most 10 s: with the config lock held, the holder cannot be inside its record section); with the apply flock free by `LOCK_NB` it stops an orphaned build unit whose InvocationID still matches (by `apply/active` read again under the flock, which it clears once nothing of that unit runs, so later passes ask PID 1 nothing) and resolves `inflight.json` (`unknown` with a warning, unless an intent, a record or a rejecting verdict in `seen` exists, which is rolled back); on a running instance (`cogbox init` on a live one) it leaves both alone. It then finishes pending rollbacks (sweeping intent tmp names only with the flock), empties the trash with `--init-only`, and exits 78 with the stamped message when an intent remains on a stopped instance. The launcher does not rely on that exit: whatever the verb did (it may have crashed, been killed, or be missing), it looks for `apply/rollback/*.intent` itself and, on a stopped instance, exits 78 before any boot snapshot or promotion, printing `cogbox: an automatic plugin rollback could not be finished (<why>); free disk space, or run 'cogbox plugin apply --abandon-rollback -n NAME'` unless the verb printed it. Whether the instance runs is its lifetime lock (`<runtime>.lock`), probed with a momentary shared lock; on a running instance a pending intent only warns, because a live apply may have just written it.
- **GCE/PVE.** The cogbox wrapper bakes `COGBOX_APPLY_TIMEOUT=5340`, `COGBOX_APPLY_BUILD_TIMEOUT=1800` and `COGBOX_APPLY_MIN_AVAILABLE_MB=2048` as defaults (`--set-default`), and not `COGBOX_APPLY_WAIT_MAX`, so a value a caller puts in the command's environment (the control plane is to pass 90 s once it drives live apply) always reaches cogbox. The supervisor tees `cogbox init`'s output into `${XDG_RUNTIME_DIR}/cogworx-last-init.log` (tmpfs) as well as the state disk's `last-init-error.log`, and summarizes the tmpfs copy: a full or read-only state disk, the usual cause of exit 78, still publishes the stamped line as `cogworx/boot-error`. Its OOM drain bounds `cogbox stop` at 75 s (stop's 65 s plus the 5 s apply step).

## Launch-time patching

Runtime settings (vcpu, memory, ports) are applied by patching the microvm runner script's QEMU arguments at launch time. Settings that affect the guest (overlay sizes, SSH keys) are written to the instance's data directory where systemd services inside the VM pick them up at boot. The wrapper patches the static QEMU runner's 9p share source paths to point at the instance-specific runtime directory, so the same VM image serves all instances.

Additional host directories avoid runner text injection. Cogbox owns `microvm.extraArgsScript`, which executes `additional-dir-args` after the sentinel rewrite; every generated `-fsdev` references only `additional-dirs/N`. The paired `system-additional-dirs` fw_cfg manifest carries the canonical target and access mode. `cogbox-additional-dirs.service` validates the complete manifest, rejects guest-state and special-filesystem collisions, and mounts each 9p tag at the same canonical absolute path before sshd. Read-only grants are enforced both by QEMU's `readonly=true` export and the guest's `ro` mount option.

Single-file injections (harness auth tokens, the L7 CA certificate, and the additional-directory manifest) go through QEMU's `fw_cfg` instead of a static 9p share: the wrapper passes `-fw_cfg name=opt/<tag>,file=<source>` and a guest systemd service consumes the blob from `/sys/firmware/qemu_fw_cfg` at boot.

Dynamic host-directory grants apply to both workstation and hosted QEMU runners because this plumbing lives in the shared VM module. The container target deliberately has no equivalent: OCI and Kubernetes deployments must select host-directory mounts in their orchestrator, and `cogbox-container` has no VM runner. It declares no `cogbox-additional-dirs.service` either: the unit reads the fw_cfg manifest, which cannot exist in a container, so it would fail at every boot and leave the system degraded (pinned by `checks.guest-additional-dirs-vm-only`).

## Guest extension re-exec

Two sources of guest extension share one mechanism, `--override-input userExtensions`:

1. With [plugins](plugins.md) installed (`.plugins` non-empty in config.json), the wrapper re-execs `nix run` with `userExtensions` pointing at the generated `plugins-flake/`, which composes every plugin module plus the user flake.
2. Otherwise, if the [per-instance flake](extensions.md) differs from the scaffold, `userExtensions` points at `flake/` directly. A pristine scaffold skips the re-exec entirely (the closure would be identical to the baked-in one, and re-evaluating the cogbox flake needs its inputs fetchable).

`COGBOX_REEXECED` breaks the loop after one hop. Non-launch verbs never re-exec.

The cogbox wrapper also exports `COGBOX_BASE_RUNNER`, its own runner (the one it boots for an instance with neither plugins nor a customized per-instance flake), as a default (`--set-default`). The second hop is a cogbox package built from the composed runner, but it inherits the first hop's environment, so in both hops the variable names the image's base runner. No cogbox verb reads it yet.

The plugins re-exec evaluates a copy of the composition, never `plugins-flake/` itself: the launcher releases the instance config lock before the eval, and a `cogbox plugin` op that commits meanwhile must not leave a runner record for bytes other than the ones that runner was built from. The copy is the daemon pass's boot snapshot (below) when that is complete, otherwise a plain copy in `apply/pin/<id>/` (init passes, or a failed take). Only when that copy cannot be written either does the eval read `plugins-flake/` directly, as it did before. The pinned bytes' `comp`, sha256(flake.nix, a NUL byte, flake.lock) in lowercase hex, travels to the second hop as `COGBOX_BOOT_COMP`. A composition without a `flake.lock` (a plugin op's `nix flake lock` failure only warns) hashes an empty lock, in the launcher and in `snapshot.compOfDir` alike, so it keeps a comp and a fast path; nix refuses a zero-length lock, so no runner is ever recorded for one that shares it.

`runner.path`, the skip-eval fast-path record, has three lines: the record key (`<flakeSource>#<reexecPackage>`), the composed runner, and the `comp` of the composition that runner was built from. Every writer (the re-exec's self-record, `prebuildAndPushRunner` on k8s) writes the third line, and the fast path requires it to be present and equal to the `comp` of the bytes the boot would evaluate. A two-line record from an older cogbox, or one whose composition changed after it was written, therefore costs one re-exec, which rewrites it. Older launchers read only the first two lines.

### Boot snapshot (live-apply state)

The daemon pass records exactly what the running guest booted under `<icd>/apply/`. An init-only pass boots nothing and writes only the composition pins its re-exec evaluates (`apply/pin/<id>/`). A [live plugin apply](#live-plugin-apply) checks a change against it (`base` is what the guest runs) and rolls a rejected change back to it.

- **Take.** Before the fast-path check, under the config lock, the daemon pass writes `apply/snap/<id>/`: `composition/{flake.nix,flake.lock}` as byte copies (never hard links, because nix rewrites a `path:` flake's lock in place), `state.json` (the plugin entries and their tagged L4, L7 and inject policy), `src/` as a `cp -al` of `plugin-sources/` (the only hard-linked part; `materializeSource` copies with `--remove-destination`, so no verb rewrites a shared inode), and `meta.json` = `{id, comp, runner, key}` last. A composition without a `flake.lock` is copied without one. A snapshot without `meta.json` is incomplete and is never used. Its id goes to `apply/booting`. The whole take is bounded at 20 s (`COGBOX_BOOT_SNAPSHOT_TIMEOUT`, whole seconds as bash counts them), with each fsync at most 5 s of that, because it runs inside `cogbox start`'s 60 s and its `cp -al` grows with the source tree (a large `?dir=` plugin on a cold or network-backed disk); past the bound it fails like any other take.
- **Promote.** Right after winning the lifetime lock, while the config lock is still held, the pass records its runner and key in the snapshot's `meta.json` and flips the `apply/base` symlink to it (an atomic rename). Without a complete snapshot it unlinks `apply/base` instead, so `base` never names an earlier boot. `apply/built` and `apply/booting` are dropped. A symlinked `apply/` is never written through (the take, the pin, the promotion and the GC all refuse it).
- **Record.** Before QEMU starts, `$RUNTIME/booted-runner` gets the key, the runner and the `comp` (`none` with no plugin composition), and `nix-store --add-root <icd>/gcroots/booted` roots the runner (bounded at 10 s); once it is rooted, `gcroots/applied/` is cleared. The root outlives the boot: a stopped instance keeps its last booted runner's closure from `nix-collect-garbage` until its next boot replaces the root or `cogbox delete` removes the instance, so after a cogbox upgrade each stopped instance holds its old image's runner until then.
- **GC.** At the take and at the promotion, every snapshot that is incomplete, or complete and named by nothing (`base`, `built`, `booting`, or the snapshot ids in `apply/active`, `apply/inflight.json` and `apply/rollback/*.intent`), and every pin older than an hour, is renamed into `apply/trash/`. When `apply/active`, `apply/inflight.json` or an intent does not parse, the GC cannot know what it names and keeps every snapshot, the incomplete ones included, with a warning. It also removes the `.booting.tmp.*` and `.base.tmp.*` names a killed launcher left (only a config-lock holder writes them). That is an O(1) rename, so the daemon pass, which must own a live QEMU within `cogbox start`'s 60 s, never deletes a tree, except a failed take's own partial tree when the take ran the disk out of room (bounded, below); its only O(files) steps are the `cp -al` and, on a disk without much room to spare, its sizing walk. The trash is emptied, bounded at 30 s, by `cogbox __plugin-apply-preboot <icd> --init-only`, which the launcher runs right after taking the config lock in every pass once `apply/` exists, passing `--init-only` exactly when the pass is init-only (`cogbox start` runs one before its daemon pass). The launcher bounds that call at 360 s (TERM, then KILL 5 s later; the verb's legs are listed under "Plugin changes, stop, delete and the launcher" above), since the verb's own 30 s trash budget is checked only between entries.
- **Disk.** Because `src/` hard-links every booted plugin file, removing or updating a plugin frees nothing at once: the booted version's files stay allocated, held by `apply/base`, until the next boot's promotion moves that snapshot into the trash and the init pass of the boot after that empties it (two `cogbox start`s; nothing reclaims them while the instance stays stopped). Updating a large plugin on a nearly full disk can therefore need room for both versions.
- **Free-space floor.** The take, the pin and the `gcroots/booted` root all write to the filesystem that holds `<icd>`, and whatever a take used stays used until the next init pass empties the trash, while the rest of the pass (`.app-launch`, on that same disk on GCE and PVE) still has to write. Below `COGBOX_APPLY_MIN_FREE_MB` (64) of blocks available to an unprivileged writer, or 16384 free inodes on a filesystem that counts them, the pass skips all three with one warning and boots as a launcher without live apply does: no base, and a re-exec straight from `plugins-flake/` with the comp of those bytes.
- **Take size.** Passing the floor does not mean a take fits above it. Hard links cost nothing, but the `cp -al` costs one inode and the blocks of every directory of `plugin-sources/`, and a `?dir=` plugin brings its whole repository, so the take is sized against the room above the floor (less a margin of 64 inodes and 1 MiB for the snapshot's own files) before anything is written. When that room is at least what the whole filesystem uses, the tree cannot exceed it and nothing is walked. Otherwise `find plugin-sources -type d -printf '%k\n'` counts the directories and sums their KiB, stopping once either exceeds the room, within the take's bound. A tree that does not fit skips the take with one warning, and the pass boots without a base as after a failed take (a re-exec still evaluates a pin, which fits within the floor). The cogbox wrapper puts `findutils` on the launcher's `PATH` for this; a walk that cannot run counts as fitting.
- **A take that runs out of room anyway** (the walk's estimate was off, or something else filled the disk meanwhile) gives the space back at once: when `cp` reports ENOSPC or EDQUOT (its first three error lines are shown, in the C locale), or a fresh statfs after the failure reads under the floor, the partial tree is removed with `rm -rf --one-file-system`, bounded at half the take's bound (10 s), because a rename into the trash would free nothing until the next init pass. A removal cut short leaves the rest to the GC's rename, and the pass then writes no pin and no root, as under the floor. Any other failed take leaves its partial tree to the GC, as before. `apply/trash/` is created before the take, so the GC can still rename on a disk too full for a new directory.

None of these steps can fail a boot that boots without them, with one bounded exception below. Each one only warns and falls back: a failed take (ENOSPC, EMLINK or no free inodes in the `cp -al`, an I/O error, the bound) clears `apply/booting`, removes or leaves to the GC its partial tree (above) and boots without a base; a failed pin re-execs from `plugins-flake/`; a failed hash leaves an empty third line, which never fast-paths; a failed root, GC rename, base flip, base `meta.json` rewrite or record write, and any exit of the housekeeping verb, is only a warning. (The one refusal is not a Phase 0 step: a pending rollback intent on a stopped instance exits 78, [above](#plugin-changes-stop-delete-and-the-launcher).) The exception: a take that exhausts the disk despite its sizing, and whose partial tree then cannot be removed within its bound, leaves the remainder holding that space until the next init pass, and the rest of the pass can then fail on the full disk as it would on a disk filled by anything else.

Two concurrent `cogbox start`s of one instance still boot once, because only the winner of the lifetime lock proceeds, but when both miss the fast path the loser may fail with a nix error about a missing path instead of "already running": the other pass's GC can move the loser's snapshot into the trash before the loser's eval reads it. The loser's `cogbox start` exits 70 either way.

The re-exec rebuilds cogbox on the host that runs the launcher (for a hosted image, the guest host VM), so `cogbox-tools` (the zig-built `bin/cogbox` and `lib/libnetfilter.so`) is built there or substituted from a binary cache. A store path does not record the CPU its machine code was compiled for, and zig targets the build host's CPU by default: a cache entry built on a host with AVX-512 would die with SIGILL at startup on a host without it. The zig builds are therefore pinned to a fixed level (`zigCpuFlag` in `flake.nix`: `x86_64_v2+avx+aes+pclmul` on x86_64, which keeps zig std's hardware AES-GCM/GHASH paths, and `baseline` on the other Linux systems, which gives up hardware AES there so that the tools also run on aarch64 cores without the crypto extension), and `zig-tests` runs at the same level. The pin is also the x86_64 host floor: on a CPU without AVX, AES-NI or PCLMULQDQ (or a VM whose CPU model hides them, such as `qemu64`/`kvm64`) the tools die the same way, with SIGILL (exit status 132) at startup. `checks.x86_64-linux.cogbox-tools-isa` fails on instructions from the extensions beyond that level (`tests/check_tools_isa.sh`, a static objdump scan against a list of instruction classes, so it also catches paths a startup smoke never reaches, such as SHA extensions in std.crypto), on a lost hardware AES or carry-less-multiply path, and when `cogbox help` does not start under qemu-user on a Sandy Bridge CPU model.

## Plugin brain materialization

The base module declares the `cogbox.*` option tree and folds the merged `config.cogbox` of every plugin into one `cogbox-brain` derivation at build (per-harness native trees + merged opencode/codex/OMP MCP settings + a generated capability index skill). Two base-owned `Type=oneshot` services (modeled on `load-ssh-keys`, ordered `before=sshd.service`) materialize it at boot:

1. `cogbox-brain-materialize` runs after backend state is available and creates the `~/work` (`/root/work` -> `/var/lib/cogbox/work`) symlink, the `~/work/.cogbox/brain` link to the RO store derivation, and per-leaf child symlinks into each harness's real writable dirs (`.claude/skills/<s>`, `.opencode/agents/<a>.md`, `.omp/rules/<r>.md`, `.agents/skills/<s>`, etc.). Before linking it prunes stale links: every symlink in those harness dirs, plus `~/work/.claude/settings.json`, `~/work/.mcp.json` and `~/work/.omp/mcp.json`, whose target is inside an earlier `/nix/store/*-cogbox-brain` path is removed, so a removed plugin's skills, commands, hooks and MCP servers stop applying at the next boot (and an old-brain `.mcp.json` no longer blocks the only-if-absent relink). A link counts only when the store entry itself is a `*-cogbox-brain` (a `-cogbox-brain` deeper in some other store path does not). Regular files, directories, links into the current brain and links anywhere else are never touched (`checks.brain-linkleaves-prune`). A container boot that cannot build the brain falls back to the plugin-less base brain (see `brain.fallback`): no plugin skills, agents, commands, rules or tools, and the prune also removes the links earlier boots left into the previous brain, so nothing from it lingers; the plugin links come back at the next boot whose rebuild succeeds. When Hermes is enabled, it creates the managed runtime skeleton (`~/.hermes/{cron,sessions,logs,memories}`) after the persistent Hermes home is ready and before materializing Hermes skills. In the VM these writes land in the Hermes overlay upper. In the container `/root/.hermes` is linked to the per-instance state PVC at `/var/lib/cogbox-state/hermes-home`; setup replaces only an empty image-scaffold directory and fails closed on a nonempty directory, wrong symlink, or invalid persistent target.
2. `cogbox-brain-trust` pre-accepts Claude Code workspace trust for `~/work` (both `/root/work` and the `/var/lib/cogbox/work` it resolves to) and reconciles stale pre-migration project keys.

The workdir/cwd is base-owned: `programs.bash.loginShellInit` and the harness launchers (`c`/`oc`/`om`/`cx`/`h`/`p`) `cd ~/work` (the launcher also exports `OPENCODE_CONFIG` and merges `cogbox.env`). The contract has no `loginShellInit`/`cwd` surface, so a plugin cannot fight over cwd. See [plugins](plugins.md) for the full contract.

On the container target, `cogbox-toplevel-reconcile` runs `cogbox plugin reconcile` after `multi-user.target` to build and record the per-instance full toplevel the next boot uses. It is best-effort but loud. The verb exits 0 even when the build fails (every failure path only warns), so a failure is a nonzero exit or a `(boot uses baked base)` warning in its output. A failure prints a `cogbox-toplevel-reconcile: FAILED rc=N attempts=M` journal line and writes `instances/<name>/toplevel.reconcile-failed` beside `toplevel.path` (line 1 `time=... rc=... attempts=...`, then the last 40 lines of the verb's output, which carry nix's error lines or the verb's own error message); a clean run removes it. Only this boot unit writes or clears the marker, so it describes the last BOOT reconcile: a later successful build outside it (a live plugin add on the running pod, or the control plane's stopped-instance reconcile) rewrites `toplevel.path` but leaves the marker, so compare its `time=` with `toplevel.path`'s mtime. The pod's nix builds without a sandbox, so a derivation that writes `$HOME` (a Go build) can leave nix's sentinel `/homeless-shelter` behind, and every later derivation then aborts on it. The unit removes it before each attempt and after the last, and retries, up to 3 attempts, while a failed attempt leaves it behind (keyed on the sentinel itself, since nix's own message about it rarely survives the verb's 600-byte stderr tail). The unit always exits 0 (`checks.container-toplevel-reconcile`).

## Runtime tool environments

Where `cogbox.runtimeEnvironment.enable` is on (by default only the hosted guest the GCE image runs), [`cogbox-env`](runtime-environment.md) selects a tool bundle at runtime. Two pieces of the guest wiring live outside `runtime/module.nix`, because `programs.bash.loginShellInit` is `mkForce`d and the launchers are generated in `flake.nix`: both guests' login init prepend `/root/work/.cogbox/runtime/current/bin` after the plugin tool bin (so it ends up first) and print a one-line warning in interactive shells when the selected bin no longer resolves, and every harness launcher puts the runtime bin first in its `PATH`.

`cogbox-runtime-restore.service` restores the selected bundle offline after a restart. It is a background unit: wanted by `multi-user.target`, ordered `After=` it and `cogbox-brain-materialize`, and never `Before=` anything, so sshd, brain materialization and readiness never wait for it. On the hosted guest it also `Wants=` and is `After=` the `nofail` work bind `var-lib-cogbox-work.mount` with `ConditionPathIsMountPoint=/var/lib/cogbox/work`, so a pool-absent boot skips it instead of letting it write under the unmounted path. It is one of the [boot-only units](#boot-only-units-once-markers): once the boot has settled, a later start in the same boot is skipped. `checks.runtime-environment` and `cogbox-guest-pool-degradable` assert that graph on the realized units, and `checks.runtime-boot-restore` boots it.

## Guest environment and non-Nix binaries

The L7 CA-trust env (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, …, all pointing at the assembled `/run/cogbox/ca-bundle.crt`) is set both as `environment.variables` (login shells) and `environment.sessionVariables`. The latter matters because the container sshd runs `UsePAM yes`, so `pam_env` delivers `sessionVariables` to *non-interactive* `ssh host cmd` execs — which source no login shell. That is the path VS Code Remote-SSH uses, so its server and tools see the CA bundle.

`programs.nix-ld` is enabled so downloaded, dynamically-linked non-Nix ELF binaries run in the otherwise pure-Nix guest. VS Code Remote-SSH ships a prebuilt glibc `node` (vscode-server) that expects a standard `/lib64/ld-linux` loader; nix-ld provides the `/lib64` stub loader and delivers `NIX_LD`/`NIX_LD_LIBRARY_PATH` via the same `sessionVariables`/`pam_env` mechanism. The stock library set is extended with `stdenv.cc.cc.lib`, `icu`, and `libsecret` for common VS Code extension native binaries.

## Network enforcement

In `rules` network mode, the wrapper loads a Zig shared library (`libnetfilter.so`) into passt via `LD_PRELOAD`. The library intercepts outbound socket calls (`connect`, `sendto`, `sendmsg`, `sendmmsg`) and checks destination addresses against the configured CIDR rules; denied connections receive `ENETUNREACH`. It initializes via `.init_array` (before `main()`) so all file I/O for rule loading completes before passt activates its seccomp-bpf sandbox. Rules hot-reload via `SIGUSR1`; the L7 proxy reloads via `SIGHUP`. The filter's default deny has exactly one exemption, armed only when the launcher is handed `COGBOX_MOSH_UDP_FORWARD`: passt's per-flow reply socket for an inbound datagram on that forwarded UDP range, recognised by its bound local address (see [the mosh reply-socket exemption](network-filtering.md#the-mosh-reply-socket-exemption)). Details, including the remap/SOCKS5 layer and the L7 proxy architecture, are in [network filtering](network-filtering.md).

The `cogbox rules`/`remap`/`l7`/`plugin` verbs all edit `config.json`, regenerate the runtime rules files, and signal the running processes, so policy changes take effect without restarting the VM. The CLI shares the on-disk rule format parser with the LD_PRELOAD filter, so the formats stay in sync.

## Guest reply routing

passt keeps a remote peer's real source address on the forwarded guest ports (sshd 22, the app relay 8080 and the mosh UDP range), so the guest answers a client at, say, 198.51.100.7 by routing to 198.51.100.7. Any more-specific guest route covering that address captures the replies: a Docker bridge auto-assigned from Docker's default pools, a VPN, kind/k3s, podman or a static route. The symptom is that the connecting side never gets the SSH banner (or the HTTP response, or the mosh datagram), while the guest itself looks healthy and other clients work. Every VM guest (local, GCE-hosted, Proxmox-hosted) therefore routes replies to connections that arrived on its uplink back out the uplink, even when a more-specific route in its main table covers the client's address. The container target does not carry it.

The mechanism is `modules/guest-reply-route.nix`, with its ids in flake.nix `guestReplyRoute`. `cogbox-reply-route.service` loads `table ip cogbox_reply`: a prerouting rule sets connmark bit 0x10000000 on new connections whose input interface is in link group 1000, and a `type route` output chain copies that bit to the packet mark, which reroutes the packet. The uplink gets link group 1000 from the `99-ethernet-default-dhcp` match (`Type=ether`, `Kind=!*`), so no interface name is involved; the same .network declares routing rule priority 50 (`fwmark 0x10000000/0x10000000 lookup 1000`) and table 1000 with a default route via the DHCP gateway (`onlink`; networkd also adds the lease prefix route and a host route to the gateway in that table). Guest egress, container egress and guest<->container traffic never carry the bit and keep using the main table. Diagnose with `ip -4 rule` (the priority-50 rule), `ip -4 route show table 1000` (the default via the uplink), `nft list table ip cogbox_reply` (the counters show whether anything matched) and `ip route get <peer> mark 0x10000000` (where a marked reply would go). `systemctl stop cogbox-reply-route` is the kill switch (it deletes the table) and `systemctl start cogbox-reply-route` restores it. The nft half fails open: `nft -f` is one transaction, so a failed unit leaves no table, the rule then matches nothing and routing falls back to the old behaviour. The networkd half is constants only, and networkd owns it because it deletes rules and routes it did not configure.

Residuals, all of which fall back to the old behaviour: UDP servers bound to the wildcard address (their source is chosen from the main table before netfilter runs; mosh-server's default `-s` binds the SSH_CONNECTION address and is covered); IPv6 (passt runs `-4`); a container on the colliding network still cannot reach peers in its own subnet through the guest; a peer whose address equals a guest-local address; strict reverse-path filtering set by a plugin (first packets are dropped before the mark applies); forwarded/DNAT flows, such as a container publishing a port reached through the uplink; a blackhole, unreachable or prohibit route (or rule) covering the peer, because the first route lookup fails before the output chain sees a packet; a flow whose conntrack entry is lost mid-session; and a plugin that claims the uplink with an earlier .network, disables networkd, or enables `networking.nftables` (whose flushRuleset drops the table). `checks.guest-reply-route-vm-only` pins the VM-only wiring at eval time and `checks.guest-reply-route` proves the behaviour in a nested VM against a real Docker network, including both negative controls.

## Running as another user (sudo context)

cogbox resolves the *real* (non-root) user -- whose `$HOME` holds the config, data, and harness credential files -- from `SUDO_USER`, but **only when actually running as root** (euid 0). That is the genuine `sudo cogbox` case, where cogbox acts on the invoking user's behalf and `chown`s the files it creates back to them. When not root, cogbox uses its own identity (`id` / `$HOME`).

This guard matters because `sudo` exports `SUDO_USER` for *every* invocation (including `sudo -u other`), and a non-login `su other` preserves it. So `sudo su <user>` **without** `-` leaves the invoker's `SUDO_USER`/`HOME` in the environment; without the euid guard cogbox would resolve paths to the *invoker*, not the user it now runs as, and write into a directory it can't touch. A fail-fast preflight catches this -- if the resolved home isn't writable by the current uid, cogbox aborts with actionable guidance instead of cascading permission errors.

**To run cogbox as a different user, use a login shell** -- `sudo su - <user>` (or `sudo -u <user> env -u SUDO_USER HOME=/home/<user> cogbox`) -- not `sudo su <user>`. This is the invocation a multi-user control plane must use to launch cogbox per-user.
